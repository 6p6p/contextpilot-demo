这是业务质量回归基准，不是已经通过真实服务的证明。完整结果见

## 运行

仓库根目录，Node 24/npm 11：

```sh
npm run test:corpus
npm run test:corpus -- T06
npm run check
```

复用现有 Vitest/Zod/PDF.js/PptxGenJS/JSZip，不增加框架或依赖。默认 `npm test` 和 `check`
也包含 Corpus。单例命令只执行对应 Case，其余结果为 NOT_RUN，不计入通过率分母。
JSON 结果在 `test-results/corpus-v1/results.json`，单例为 `results-T06.json`；原始 Vitest
JSON 同目录，包含 Case ID、断言、失败原因。顶层 overall 包含 hook 失败，不能仅用单项 PASS 判断全套通过。
该目录被 Git 忽略，Playwright 会清空 test-results，因此先运行 E2E，最后运行 Corpus 留存结果。
默认不加载 .env，不创建数据库连接；fetch 出站守卫失败即报错。所有模型、搜索和向量服务均未真实调用。

## 产物和人工检查

离线测试生成 `test-results/corpus-v1/management-5.pptx` 和 `management-10.pptx`；JSON保存SHA-256和文本框。
它们是 STUB规划的真实PPTX，不是本轮真实模型验收文件，不上传云端。
程序核对CRC、Content Types、关系目标、页数、16:9、备注、中文字体声明、表格业务字段，禁止不完整引文与无来源确定事实。
本轮另用 Artifact Tool 渲染15页并逐页视觉检查；独立Python包/几何检查命令记录于验收报告。
以后自动运行 Corpus 不自动等于已人工看图，视觉结果应按具体文件SHA留存。

人工用PowerPoint/WPS检查：无修复对话框；5/10页；中文字体；标题、引用和表格不溢出遮挡；“来源分析/分析判断/建议”区分正确；周宁与2026-11-08未变；P/O/M/T/L/W定位在备注可追溯。新Corpus文件原生打开仍 NOT_RUN；Phase8旧文件的人工确认不替代此项。

## 扩展与基准变更

1. 真实Bug先保存最小合成复现，增加 Case ID/失败断言，再改业务代码。复用既有辅助函数，不导入含测试注册的 .test.ts。
2. 新案例按 cases.ts schema提供版本、配置、结构化事实、允许来源、禁止项、客观通过条件和需要的层级；在现有 Vitest 下命名 `Txx ...`。目前runner允许T01–T08，扩展时同步ID边界及结果枚举。
3. 预期不匹配时先诊断代码/模型/材料。禁止为使回归变绿而重写Golden。确需改变事实时新增版本目录并在变更记录说明理由、影响案例、旧新预期和评审依据。
4. `SHA256.json`固定6个输入；PDF按字节，文本归一CRLF为LF后计算。不要自动更新校验和。初版生成PDF使用现有reportlab方式：`python scripts/generate-corpus-fixtures.py`，需要本机已有reportlab；默认回归不需要Python/reportlab且不重生成PDF。
5. 真实结果分开记账，外部STUB不进入Live通过率；NOT_RUN不计入任何通过率分母。不得复制私有原始输出、Cookie、对象路径、凭据进fixtures。
6. 数据库写入必须先证明测试库与公网独立，或全部列表/检索/Worker边界真正隔离。仅worker Scope不够。当前条件未满足，禁止用现有integration命令绕过。

变更记录：v1首次引入，沿用历史合成PDF，新增同项目brief/会议和冻结MOCK证据；没有修改旧Golden事实。初跑引用断言误以为同一来源总返回完整摘要，按既有结论去重协议改成原文包含/版本/日期断言，非业务事实变更。
