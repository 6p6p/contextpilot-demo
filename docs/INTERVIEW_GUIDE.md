# ContextPilot 面试表达与演示指南

以 2026-11-07 / 2170fac 源码为基线。工程细节与证据入口见 [架构复盘](ARCHITECTURE_REVIEW.md)，本轮验证边界见 [审计](REPOSITORY_AUDIT.md)。下列口述采用开发者视角，不代表未留存的个人贡献或性能成绩。

## 1. 三种项目介绍

### 30 秒

ContextPilot 是一个 AI 决策工作台，把多轮聊天、PDF 证据问答、会议风险与待办、跨会话记忆、联网搜索和 PPT 产物串起来。重点是资料和任务能持久化，回答能回查来源，邮件必须人工确认当前版本。它是 React/Fastify/PostgreSQL 的单工作区 MVP，有真实服务集成和分层测试；目前不是多租户平台，PDF 回答也主要是经过验证的原文摘录。

### 1 分钟

我解决的是“资料分散、聊天结果难复用、会议结论难跟进”的问题。用户上传 PDF 或会议 TXT，在聊天中查询；PDF 按页分块和向量检索，会议提取带行号的风险与行动项。人工修改待办后，可以复核邮件草稿、确认精确版本，再交给受白名单限制的发送任务。聊天和会议事实进入长期记忆，后续新会话可以引用历史来源；公开短问题走 Tavily；明确生成 PPT 的指令创建后台任务，保存来源快照、规划和私有文件。后端通过 PG 行锁、租约、唯一约束处理任务恢复和重复请求。我没有让模型任意执行动作，模型负责理解和内容规划，权限与发布由服务端控制。真实验收、外部替身回归和浏览器 UI 测试分别报告。

### 3 分钟技术介绍

系统是模块化单体，React/Vite 负责对话和来源选择，Fastify 装配服务、数据库和同进程 Worker；Railway 一个服务托管静态前端和 API。业务状态在 PostgreSQL，文件在 Supabase 私有 Storage，模型和搜索通过独立适配器调用。没有 Redis，也没有多个 Agent。

聊天先在事务里创建用户消息和 processing 回复，用 clientRequestId 去重，再在事务外调用模型，结果落库。上下文只取有界的 completed 消息，历史持久化不意味着无限上下文。PDF 经 PDF.js 逐页提取，800 字符块、120 重叠，嵌入后用 pgvector cosine distance 检索；模型选择 sourceId 和原文，后端验证连续子串并由块绑定页码，因此目前是可核查摘录，不夸大为复杂综合推理。

会议模型返回结构化分析，Zod 和原文行号验证负责人、日期等事实。风险影响标明是推断，未知字段保持未知。待办用版本和锁保存人工修改，重分析不覆盖草稿。确认只冻结版本，真正发信还有开关、白名单、配额和永久去重；供应商超时进入 unknown，不自动再发。

长期记忆从聊天用户消息和已验证会议分析异步提取，保存来源组、证据和观察时间，不把同名当同一人。搜索曾经过复杂 Claim/Quote 和二次审核，但真实回放暴露协议失败与过度拒绝，后来普通公开问答改成一次自然综合，保留真实来源 URL 和查询时间，接受逐句机械保障减弱的代价。

PPT 请求由规则路由进持久化 job，读取显式文件和人工待办版本，模型只规划内容页，服务端做引用、必需事实和质量校验，PptxGenJS 渲染后上传读回核 SHA，才允许私有下载。Worker 用 SKIP LOCKED、租约 token 和心跳处理接管，旧 token 不能发布；PG 与外部 API 仍非原子事务。我最关注的是证据、人工授权和失败恢复，而不是宣称自主 Agent 或生产高可用。

## 2. 8–12 分钟演示

使用 [Demo Kit](../demo/README.md) 的合成文件与 [验收表](../demo/acceptance-checklist.md)，不要展示真实凭据或个人资料。模型/队列慢时切换已完成任务讲机制，真实失败照实记录。

| 时间 | 操作与讲述 | 应核对的结果 |
| --- | --- | --- |
| 0–1 分钟 | 口令进入、新会话两轮追问，刷新 | 历史来自数据库，解释有界上下文 |
| 1–3 分钟 | 上传 PDF，等 ready，选定文件提问及无依据问题 | 页码、引文与 PDF 对照；不足时拒绝补造 |
| 3–5 分钟 | 上传 TXT，展开风险行号，修改待办负责人/日期 | 区分原文事实、潜在风险、人工值 |
| 5–6 分钟 | 编辑草稿、保存、确认，再修改一次 | 旧确认失效；无授权收件箱只演示到确认，不为演示临时开邮件 |
| 6–7 分钟 | 新会话查询已有记忆 | 来源和观察时间；未知人物信息保持未知 |
| 7–8 分钟 | 公共短问题切 off/required | off 不核实时效；required 展示实际来源与查询时间，人工打开核对 |
| 8–10 分钟 | 选择 PDF/会议生成明确页数 PPT | 立即排队，解释规划/渲染/ready；下载并原生打开已完成文件 |
| 10–12 分钟 | 刷新恢复任务、展示测试分层与限制 | 没有重新生成同一产物冒充恢复；单工作区、非高可用边界 |

## 3. 六模块讲解卡

| 模块 | 面试时抓住的数据流 | 关键入口与容易说错的点 |
| --- | --- | --- |
| 聊天 | 事务占位 → 有界上下文 → 模型 → 消息状态 | `chat/service.ts:send`、`context.ts:buildContext`；归档是保留式，失败请求 ID 重放不自动重新生成 |
| PDF | 私有上传 → 按页字符块 → 嵌入 → SQL cosine → 选原文 → 校验引用 | `knowledge/pdf.ts`、`retrieval.ts`；PPT 读指定 PDF 的流程与 RAG top-k 不同；无 OCR/ANN 承诺 |
| 会议/邮件 | 分段分析 → 行号校验 → 风险/待办 → 人工编辑 → 版本确认 → send job | `meetings/analysis.ts`、`email/service.ts`；accepted 不是 delivered，unknown 不自动重发 |
| 记忆 | 源消息/分析事务入队 → 抽取验证 → 来源化事实 → 词法优先召回 | `memory/extraction.ts`、`service.ts`；没有全局人物图谱、自动事实覆盖 |
| 搜索 | off/auto/required → 公共短查询 → Tavily → 一次自然综合 → 元数据持久化 | `search/public.ts`；旧 Claim 回归还在，但不是当前聊天发布链路 |
| PPT | 明确意图 → job → 来源快照/规划 → 校验 → 渲染 → Storage 读回 → 下载 | `presentations/service.ts`、`plan.ts`、`coverage.ts`；异步避免 HTTP 长等待，质量规则不是通用语义证明 |

以上 API 路径的完整前缀均为 `apps/api/src/`。代表难点可挑架构复盘第 7 节的 TLS、PPT 误路由、正文覆盖和邮件不确定发送，逐项按“现象—定位—修复—验证—剩余边界”讲，不把文档描述当成本轮线上结果。

## 4. 面试问答（每题包含核心、原理、实现、取舍与追问）

### 基础

**1. 这个项目解决什么问题？**

- 核心：把零散资料和对话转成有出处、可跟进、可恢复的工作结果。
- 原理：事实来源、状态与动作分开管理。
- 实现：六模块共享 PG 关系数据，文件进私有 Storage，消息保存引用。
- 取舍：只做共享 Demo，不能承诺团队隐私隔离。
- 追问：哪个场景必须跨模块？用会议待办到邮件/PPT 的人工值传播举例。

**2. 六项能力如何形成闭环？**

- 核心：资料理解、讨论、风险跟进、历史复用和汇报形成闭环。
- 原理：复用明确来源，而不是复制模型答案当事实。
- 实现：会议分析入 memoryJob，PPT 读取人工待办，邮件读取确认快照。
- 取舍：并非自主一键完成所有动作，邮件有人工关口。
- 追问：哪一步不可由模型授权？发送与配置变更。

**3. 为什么 TypeScript 之外还用 Zod？**

- 核心：网络和模型输出不受编译器约束。
- 原理：静态类型约束开发，运行时 Schema 拒绝不合法输入。
- 实现：shared 契约、parseAnalysis、verifyPlan；引用还做原文核对。
- 取舍：结构正确不能证明语义正确。
- 追问：合法 JSON 但错误事实怎么处理？按来源验证并保留人工核查。

**4. 前后端怎么分工？**

- 核心：前端管理交互，后端管理权限、模型、持久化和发布。
- 原理：不能信任浏览器提交的来源/权限声明。
- 实现：App/ChatWorkspace 向 Fastify routes 请求，service 执行事务；生产同源托管。
- 取舍：轮询不是实时流式推送。
- 追问：密钥在哪里？服务端配置，不能打包进 VITE。

**5. 聊天如何记住上下文？**

- 核心：从数据库恢复 completed 消息，截取有界历史给模型。
- 原理：模型无会话数据库，应用重建 messages 数组。
- 实现：buildContext 最近 20 条/24000 字符；历史接口最近 200 条。
- 取舍：旧消息会超出模型窗口，没有摘要压缩。
- 追问：超长单条消息？字符预算可能截掉上下文，不能称无限记忆。

**6. 怎么证明六功能是真的？**

- 核心：代码接入、真实服务记录和人工结果分别提供证据。
- 原理：替身能验证控制流，不能证明供应商当前可用。
- 实现：unit、真实 PG integration、live suites 与 demo 验收报告分层。
- 取舍：本轮离线通过不覆盖公网复验，历史报告也有 FAIL/NOT_RUN。
- 追问：现场服务失败怎么办？如实展示错误和历史证据，不切 Mock 冒充。

### 中级

**7. 为什么不用整份 PDF Prompt？**

- 核心：检索缩小输入并绑定可回查页码。
- 原理：窗口、成本、长文注意力和来源定位都有边界。
- 实现：chunkPages 每页 800/120 字符，retrieve top8 后阈值过滤。
- 取舍：切分和 top-k 也会遗漏，不保证比全文所有场景更好。
- 追问：表格/扫描件？文本结构可能丢失，当前无 OCR。

**8. Embedding 是哪个模型、多少维？**

- 核心：历史真实验收用 BAAI/bge-m3/1024，运行时由配置决定。
- 原理：同维度不意味着相同语义空间。
- 实现：createEmbedder 对 endpoint/model/dimensions hash，检索过滤 space 和维度。
- 取舍：换模型要重嵌入，不能混搜旧向量。
- 追问：现在生产值？未读取部署配置就不能保证。

**9. pgvector 如何做检索？**

- 核心：cosineDistance 排序并按来源范围过滤。
- 原理：1-distance 是余弦相似度，需阈值和候选截断。
- 实现：createRetriever 在 ready、space、dimensions、selected IDs 内查。
- 取舍：当前无 HNSW/IVFFlat，不能报未测的百万级延迟。
- 追问：如何扩展？先测数据量与查询计划，再加兼容索引/召回评估。

**10. 怎么避免引用错 PDF？**

- 核心：模型只选本次候选 ID，页码和文件身份由服务器绑定。
- 原理：引用标签不能来自模型自由文本。
- 实现：verifyEvidence 检查 sourceId 和连续 quote，再映射 documentId/page。
- 取舍：原文存在不证明回答完整，未给 IDs 的调用可全库检索。
- 追问：无证据？直接不足，不补造回答。

**11. 会议风险是规则还是模型识别？**

- 核心：LLM 判断潜在风险，后端验证结构与证据。
- 原理：风险是基于事实的分析，不是逐字事实本身。
- 实现：analyzeTranscript 分段/合并，parseAnalysis 核对行号和事实字段。
- 取舍：启发式分类可能误判提议和决定，需要复核。
- 追问：后段已解决前段风险？合并提示考虑跨段状态，但仍不保证完整。

**12. 人工待办会被重分析覆盖吗？**

- 核心：同来源待办冲突更新只改分析/风险关联，保留人工字段。
- 原理：模型再分析不是用户修改的上级权威。
- 实现：meetingTodos sourceKey、sameAction 匹配、version 和会议行锁。
- 取舍：匹配启发式可能形成新项，旧项不会自动全清。
- 追问：两个页面同时编辑？后到旧 version 得 409。

**13. 长期记忆和历史记录有什么不同？**

- 核心：历史按会话恢复，记忆是带来源的跨会话事实子集。
- 原理：提取和检索比携带全部聊天更有界。
- 实现：memoryJobs → extractChat/extractMeeting → memories → retrieve。
- 取舍：抽取会遗漏，词法优先而非完整 hybrid rank。
- 追问：没有 Embedding？可保存无向量事实并词法召回。

**14. 同名人物和冲突事实怎么处理？**

- 核心：不按姓名跨来源合并，也不自动覆盖冲突。
- 原理：来源身份与观察时间不等于实体唯一身份和事实有效时间。
- 实现：sourceGroup + fingerprint，引用保留 parentId/observedAt。
- 取舍：没有实体解析或冲突裁决引擎。
- 追问：要产品化怎么办？显式实体 ID、有效期/撤回状态与人工确认。

**15. 模型会自主调用工具吗？**

- 核心：当前是服务端受控编排，没有开放式 function-calling 循环。
- 原理：用户意图映射确定的权限范围和服务链路。
- 实现：needsSearch、isPresentationIntent、显式文件选择。
- 取舍：规则有误判，但行为更容易解释和测试。
- 追问：为什么称 Agent？可称有记忆和任务执行的 AI 工作台，不夸成自主多 Agent。

**16. 三种搜索模式怎么工作？**

- 核心：off 不查，auto 时效关键词触发，required 强制查询。
- 原理：搜索动作必须可见且受控。
- 实现：needsSearch，混合 RAG 用 explicitPublicClause，Tavily 元数据随消息保存。
- 取舍：auto 非语义分类；required 仍会被隐私门禁拒绝。
- 追问：查询时间能证明最新吗？不能，它只是获取结果的时间。

**17. 为什么删除复杂搜索审核链路？**

- 核心：真实回放显示结构与审核协议增加失败，普通回答改成一次自然综合。
- 原理：增加校验层也会增加模型协议失败与误拒。
- 实现：chat 调 answerPublicSearch；旧 answerWithSearch 仍供回归。
- 取舍：来源链接可信不等于每句内容绑定，逐句保证减弱。
- 追问：准确率提高多少？没有统一评测数据，不报数字。

**18. PPT 为什么不是直接调用模型生成文件？**

- 核心：模型规划结构化内容，确定性渲染器生成 PPTX。
- 原理：内容、证据、格式和文件发布各自校验。
- 实现：planPresentation → verifyPlan/verifyContentQuality → renderPresentation → SHA 读回。
- 取舍：样式有限，语义质量仍需原生打开与人工检查。
- 追问：没有资料能生成吗？能生成通用主题建议，不能伪造企业事实。

**19. PPT 如何避免旧待办发布？**

- 核心：快照保存版本，发布前再次锁行核对。
- 原理：规划耗时期间人工可能已修改来源。
- 实现：assertCurrentPresentationTodos 在规划前及 ready 事务检查 version/owner/date/status/ignored。
- 取舍：不是所有来源变化都有同等锁；历史 ready 文件仍是旧快照。
- 追问：中途变化怎么办？任务失败保留证据，人工复核后新任务。

### 高级与压力追问

**20. 为什么不用 Redis/BullMQ？**

- 核心：当前 PG 已能事务入队与租约领取，少一个基础设施。
- 原理：行锁、SKIP LOCKED、状态和 token 构成持久队列。
- 实现：各 processOne 和 startDocumentWorker。
- 取舍：调度、监控与重试逻辑自己维护；不是说 Redis 没价值。
- 追问：何时引入？数据库轮询/吞吐或复杂调度成为实测瓶颈后。

**21. 两个 Worker 会重复处理吗？**

- 核心：锁防同时领取，租约 token 防过期结果发布，但不能保证外部调用不重复。
- 原理：短领取事务与长外部操作分离，需要 fencing 条件。
- 实现：SKIP LOCKED、心跳、owns 条件写回；历史双池测试。
- 取舍：超时接管时旧模型调用可能还在运行。
- 追问：邮件怎么办？不确定发送转 unknown，不按普通生成任务重发。

**22. 进程重启能恢复哪些东西？**

- 核心：历史、任务与文件可恢复，未完成普通聊天不会自动重放。
- 原理：持久状态与租约过期是恢复依据。
- 实现：PG job、Storage，processing 聊天过期标失败；PPT 保存 sources/plan。
- 取舍：恢复依赖配置一致、Worker 启用及服务可达。
- 追问：恢复测试等于高可用？不等于；Railway 当前一个副本。

**23. 数据库和 Storage 如何保持一致？**

- 核心：状态机和上传读回验证控制发布，不是跨系统原子事务。
- 原理：外部对象不能加入普通 PG 事务，需要可检测中间态。
- 实现：storageReady、PPT SHA/size/readback、不同对象冲突拒绝覆盖。
- 取舍：可能残留对象/失败任务，不能随便自动清理审计证据。
- 追问：如何补偿？受控对账和授权清理，不能全桶删除。

**24. 邮件失败是否自动重试？**

- 核心：可能发送过的请求不自动重发，以免真实重复收件。
- 原理：网络超时无法证明供应商未执行。
- 实现：unknown、providerMessageId、状态核查、draft/version 永久唯一键。
- 取舍：牺牲自动恢复便利，保留人工核查成本。
- 追问：accepted 与 delivered？前者仅受理，后者还需投递事件/实际收件证据。

**25. 如何保证用户确认的是发送内容？**

- 核心：确认绑定精确草稿版本和快照，不绑定一句模糊“同意”。
- 原理：编辑、重新分析和待办变化都可能使原授权失效。
- 实现：matchesConfirmation、analysisId/changedTodos 校验、冻结 delivery payload。
- 取舍：确认与发送分离增加一步，但防误发。
- 追问：确认后修改？旧确认失效，必须重新复核保存版本。

**26. 单工作区有什么安全局限？**

- 核心：共享口令提供入口保护，没有不同访客的资源隔离。
- 原理：认证某个工作区口令不等于认证独立用户。
- 实现：HMAC Cookie、API hook；Schema 无 tenant/owner。
- 取舍：适合合成资料演示，不适合互不信任客户上传。
- 追问：如何多租户？身份、成员关系、所有权查询/RLS、job/Storage scope 与越权测试一起做。

**27. 如何防 Prompt Injection 和数据泄露？**

- 核心：不可信内容不能授权动作，模型选择还须后端验证。
- 原理：权限与数据通道分离，多层验证降低风险。
- 实现：原文核对、Zod、白名单、独立 publicQuery、不自动搜索内部上下文。
- 取舍：提示/关键词不构成绝对隔离或完整 DLP。
- 追问：LLM 服务本身收到内部资料吗？处理任务确需发送选定内容，产品化需明确供应商与数据政策。

**28. 为什么不直接用 LangChain/LangGraph？**

- 核心：当前少量固定链路直接用 TS 服务更便于控制事务和权限。
- 原理：框架可组织工具/状态，但不会自动解决证据、幂等和确认。
- 实现：ChatModel/SearchProvider/PrivateStorage 接口加显式 service 状态机。
- 取舍：手写编排增加维护成本，复杂动态流程时可重新评估；这是基于实现的解释，不虚构当时选型调研。
- 追问：如何证明可维护？用明确接口和失败回归举例，不说框架一定更差。

**29. LLM 幻觉怎么解决？**

- 核心：约束证据和发布边界，无法保证完全消除。
- 原理：结构合法、引文存在、语义支持是不同层次。
- 实现：PDF/记忆偏摘录，会议核事实，PPT 分事实/分析/建议，搜索保留真实来源。
- 取舍：严格模块牺牲表达自由，搜索简化牺牲逐句绑定。
- 追问：如何评估？固定语料测遗漏/错误绑定/拒答，再用真实服务和人工评审，不能只看 HTTP200。

**30. 还存在哪些可靠性风险？**

- 核心：同配置 Worker 共队列、进程配额非硬预算、跨系统非原子、个别上传 500 未复现。
- 原理：局部锁不能覆盖外部系统与所有来源生命周期。
- 实现：配置空间隔离、租约、错误码已有；报告保留 OPEN 与 NOT_RUN。
- 取舍：没有压测、灾备、全来源发布竞态证明，不伪装成熟 SaaS。
- 追问：下一步优先什么？先身份/数据隔离、故障注入与可观测性、真实质量评测，再扩展功能。

## 5. 最值得强调的三个亮点

1. **证据与权限分开**：模型提取/规划，服务端核对来源和版本；邮件授权永远来自用户明确操作。
2. **持久任务与失败边界**：PG 事务入队、租约、旧 token 发布隔离，Storage 读回校验和 unknown 邮件策略。
3. **基于失败证据做取舍**：搜索审核简化、PPT 意图误判与正文覆盖修复，都有脱敏回放、分层验证和未通过记录。

不能夸大：不说多租户、完全自主 Agent、消除幻觉、所有任务 exactly-once、生产高并发已验证、所有网页实时、所有 PDF 可理解、所有原生 PPT 均已复验。也不能把用户最终确认替换为源码可独立证明的线上状态。本轮没有云端/真实服务复验。

产品化优先顺序：独立用户与所有权隔离；敏感数据/供应商边界；可观测性与任务故障注入；检索/事实覆盖/搜索时效质量评测；配额与成本账本；备份恢复与对象对账。先验证瓶颈，再考虑 ANN、独立 Worker 或队列平台。
